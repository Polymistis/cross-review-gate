# v2.2 Grok fallback reviewer

Status: API adapter implemented 2026-09-07; CLI integration added to use the
existing local Grok Build login. Source review, packaging and live operation remain separate verification
claims. `docs/v2.2-plan.md` owns release scope.

## Configuration and authority

Central paired workflows ship `scripts/grok/auto-review.ps1`. Legacy per-project
entry points retain Codex/Claude routing; attached projects use the central
coordinator. No third full wrapper copy, primary-provider selection, manual skip
or implementer override is introduced.

Existing `reviewer-policy default` keeps Grok disabled. Following operator
authorization for xAI transmission of software/private governance and the selected account usage,
review an explicit configuration change through the existing gate. The provider
record immediately follows the consistency record, before private inventory:

```text
reviewer-policy grok-fallback
consistency-document <existing selection>
grok-provider api grok-4.6 xhigh environment-key
```

For an existing Grok Build login, select the CLI transport instead:

```text
grok-provider cli grok-4.6 xhigh local-login
```

The transport is explicit; failed API authentication never silently selects a
different account or transport. CLI discovery uses `grok.exe` on PATH or the
standard Windows user installation under `.grok/bin/grok.exe`.

This grammar fragment is not a consumer configuration change. Only governing
configuration permits the route; candidate configuration cannot enable the
current review. Supply the API key externally as `XAI_API_KEY`. The adapter
acquires the key only inside a configured live review, after input validation
and request bounds, and never prints or archives the key. Installing the adapter
or having credentials does not enable any project or spend API credit. CLI
subscription availability is not API credit. No provider quality/quota comparison
is established.

## Transport and input

The fixed Responses endpoint is `https://api.x.ai/v1/responses`. Requests use
`grok-4.6`, `reasoning.effort=xhigh`, `store=false`, `stream=false`, no tools,
`tool_choice=none`, disabled truncation and 32,768 maximum output tokens.
Redirects, automatic retries, conversation reuse, background work, candidate-code
execution and external URL fetches are disabled. No alternate API endpoint is
accepted. [Responses reference](https://docs.x.ai/developers/rest-api-reference/inference/responses),
[bearer authentication](https://docs.x.ai/developers/rest-api-reference/inference).

Grok 4.6 supports `xhigh` as the maximum effort. Requested effort is not proof of
internal work: canonical artifacts label the requested model and effort; each
private response retains the reported model and reasoning metadata. Missing
reasoning effort is not fabricated; a reported different effort refuses. The
reported model accepts the exact `grok-4.6` alias or the same family with a bounded
date suffix, matching the documented stable-alias/datestamped-release convention.
[Reasoning controls](https://docs.x.ai/developers/model-capabilities/text/reasoning),
[model aliases](https://docs.x.ai/developers/models#model-aliases).

The CLI route uses the installed Grok Build headless interface with explicit
`grok-4.6` and `xhigh`, fresh full-pass requests, `streaming-messages-json` output and a captured
governing prompt file. The existing gate-owned provider snapshot supplies the
complete candidate and evidence through read-only file/list/search tools.
Shell, edits, writes, MCP, subagents, web access and cross-session memory are
disabled for the review invocation; no permission bypass is used. Authentication
remains owned by Grok Build; the gate never reads or copies the saved credentials.
Raw per-pass JSON retains CLI-reported model usage, including the observed
`grok-4.6-build` model identity. The requested effort remains labeled as requested,
not asserted as provider-reported. [Headless interface](https://docs.x.ai/build/cli/headless-scripting).

Grok Build's plain `json` result aggregates progress text and the final answer.
The live review exposed a missing separator before the final verdict, so that
aggregate is not a verdict boundary. The Messages stream instead supplies a
terminal `result.result` containing only the final assistant text. The adapter
retains that complete NDJSON stream and validates terminal success, session/model
identity and the final assistant message before invoking the existing verdict
classifier. Standard error is retained separately, never mixed into JSON.

The shared paired/first-attachment host retains the validated runtime, governing
prompt, mode, consistency envelope and complete candidate namespace. For API
transport, only the gate-owned prompt enters the system message; captured buffers
and candidate files are labeled JSON data in the user message. CLI transport uses
the same captured files in the existing read-only provider snapshot, with a
runtime-owned root AGENTS.md distinguishing review instructions from candidate data.
Candidate instructions, comments
and configuration are never reviewer authority. UTF-8 files retain text; other
bytes use base64. No source or evidence is silently omitted.
The validated `PLAN-CONSISTENCY-REPORT.md` bytes also appear under the canonical
`CODEX_REVIEW_EVIDENCE/PLAN-CONSISTENCY.txt` path promised by the governing prompt,
matching the filesystem-backed provider snapshots without requiring tools.

API bounds: 32 MiB combined captured bytes, 100,000 file records, 64 MiB encoded
request, 16 MiB response, and one hour covering headers/body per pass. CLI uses
the existing snapshot bounds instead of sending every candidate file in one
request: larger repositories can exceed the API adapter's 32 MiB bound.
Provider
context-window or bound failures stop review without truncation or bypass.

## Routing and artifacts

Initial Codex/Claude order, protected-change legs and full pass counts remain
unchanged. Positive exhaustion permits the existing full alternate-provider
attempt. Only a second independently validated exhaustion permits configured
Grok as the third/final attempt. Each required pass receives a separate stateless
full request; no partial, cross-leg or historical pass credit is reused. No quota
avoidance state or `-NoClaude`/`-NoGrok` flag exists.

Successful API transport requires HTTP 200, completed response, a supported reported
model, no error/incomplete details and exactly one completed assistant text
message. Reasoning-item status may be absent; reported status must be completed.
Reported `store` must be false; absence does not override the explicit request.
CLI transport requires exit zero, a final successful `result` record with scalar
`stop_reason=end_turn`, nonempty final text and supported reported model usage.
An incomplete CLI turn cannot count as review. The terminal Messages record
reports `num_turns` but does not report `modelCalls`; missing metadata is not
invented or required merely because another output format supplies that field.
Before PowerShell JSON projection, reject duplicate or case-aliased member names
after decoding escaped spellings; unique escaped names remain valid. Comments,
trailing commas and excessive nesting/token counts are rejected. The shared
semantic verdict classifier and exact ordered pass framing must then pass; JSON
or process success alone never grants review authority. The coordinator checks
the artifact against the captured candidate and scheduled pass count.

Malformed output, authentication/transport errors, a BLOCKER, denied authority or
HTTP failure stops the operation. HTTP 429 means rate limiting, not positive
allowance exhaustion. No undocumented xAI exhaustion code is guessed and no Grok
exhaustion sidecar is emitted. [Error meanings](https://docs.x.ai/developers/debugging).

Private attempts retain the transcript, per-pass raw response JSON, canonical
verdict and applicable QUALITY follow-up capture. Grok artifacts add
`REVIEW-REQUESTED-MODEL: grok-4.6` and
`REVIEW-PROVIDER-METADATA: per-pass-response-json` after the existing ten header
records. Existing Codex/Claude artifact bytes remain compatible. Receipts permit
three attempts per leg, six across two legs, with Grok only third after two
exhausted predecessors and only under retained governing enablement. Caller
review PASS remains provider-neutral.

## Verification boundary

Verification uses source inspection, static parsing, mandatory source review,
subsequently authorized ordinary operation, and applicable functional testing.
Code unit tests remain banned; live provider qualification and ordinary gated
operations remain required for operational completion. An initial connectivity
call using installed Grok Build 1.0.13 and the saved login completed successfully
with requested `grok-4.6`/`xhigh` and reported `grok-4.6-build`. Connectivity alone
does not establish a successful gate review or completed consumer activation.
